> 「ゲームのスコアを記録したい。でもExcelは重いし、モバイルでは入力しづらい。
> ならば “自分専用の採点画面” を、AIに言葉で説明するだけで作れるようにする」——をコンセプトとした、
> iOS 向け・完全オフライン・完全無料 OSS のスコア盤ビルダーの設計書。

|---|---|

## 1. 背景・目的・コンセプト

### 1.1 背景と課題
世の中には無数のゲーム（ボード／カード／自作ルールなど）があるが、スコア計算の手段は二極化している。

- **紙とペン**: 手軽だが集計・順位付けが面倒、紛失する。
- **Excel/スプレッドシート**: 柔軟だがモバイルでは重く、入力しづらく、毎回ゼロから組むのが手間。
- **既存スコアアプリ**: 手軽だが「色・人数・ラウンド・勝利条件」程度のパラメータ調整に留まり、**画面そのもの**を自分のゲームに合わせて作り変えられない。

### 1.2 本プロダクトのコンセプト
**「スコアを記録するアプリ」ではなく「スコア画面を生み出すビルダー」** に再定義する。

ユーザーは「このゲームはこうやって点を数える」と**自然言語で説明するだけ**で、
そのゲーム専用の採点画面（ボタン配置・入力欄・計算式・勝敗判定）が自動生成される。
生成結果はテンプレートとして端末に保存され、以後はオフラインで即利用できる。

### 1.3 設計の3本柱
1. **オンデバイスAIによる画面生成** — Apple Foundation Models（iOS 26+、約3BのオンデバイスLLM）を使用。APIキー不要・通信不要・課金なし・プライバシー保護。
2. **宣言的スキーマ方式** — AIには「実行コード」ではなく**画面定義（JSONスキーマ）**を生成させ、アプリ内の固定レンダラが描画する。これにより安全性とApp Store規約（外部コード実行禁止）を両立。
3. **完全ローカル / オフラインファースト** — 記録は端末内のみ。サーバー費ゼロ。テンプレ共有はJSONファイルの受け渡しで実現（任意）。

## 2. 競合調査サマリと差別化

### 2.1 市場の現状
「スコア記録」ジャンルは**飽和**している。

- **有償/フリーミアム**: Scory（カスタムルール・勝利条件・シート/カード両ビュー）、各種スコアボード（色/テーマ/フォント/勝点ターゲット調整＋サブスク）、ScorePaper / ScoreUp など多数。
- **無償/OSS**: ScoreHub・Scoreboard（F-Droid、テーブル入力・完全オフライン・端末内保存）、Board buddy、My Score Keeper（React Native）など。
- **セルフホスト型Web**: MeepleStats（採点カテゴリを型付きで定義できる Score Sheet Creator を持つ）、BoardGameTracker など。

### 2.2 差別化の核（＝勝ち筋）
既存の「カスタマイズ」は **色・パラメータ・採点カテゴリ定義** までで、
**レイアウト・操作部品・独自計算ロジックをユーザーが組み上げる**ものは実質存在しない。
さらに「**自然言語の説明からAIが画面を生成する**」というアプローチは調査範囲では未確認。

| 観点 | 既存アプリ一般 | MeepleStats（最も近い） | 本プロダクト |
|---|---|---|---|
| 画面作成手段 | 固定UI＋設定 | カテゴリ定義フォーム | **自然言語 → AI生成** |
| レイアウト自由度 | 低（色/テーマ） | 中 | **高（部品配置を生成）** |
| 計算ロジック | プリセット | 合計程度 | **独自式・条件分岐（Lv3）** |
| 形態 | モバイル | Web/セルフホスト | **iOSネイティブ・完全オフライン** |
| 費用 | 無料〜サブスク | 自前サーバー | **完全無料・サーバー不要** |

### 2.3 評価（作る価値の判定）
- 「単なるスコア記録」としては**作る価値は薄い**（飽和、差別化困難）。
- 「**自然言語で説明する採点盤ビルダー**」として位置づければ、**明確な空白地帯**があり、作る価値は十分にある。
- 完全無料OSS・収益二の次という前提とも整合する（マネタイズ圧が低いため、尖った体験に振り切れる）。

## 3. スコープ

### 3.1 やること（In Scope / MVP〜v1）
- 自然言語によるゲーム説明 → オンデバイスAIで採点盤スキーマを生成
- 生成結果のプレビュー・手動微調整・テンプレ保存
- テンプレを用いた対局（プレイ）と記録、自動集計・順位・勝敗判定
- 対局履歴の保存・閲覧・再開・再戦
- バンドル済みプリセットテンプレ（AI非対応端末でも使えるよう数種）
- テンプレのJSONエクスポート/インポート（共有はファイル受け渡し）

### 3.2 やらないこと（Out of Scope）
- サーバー・クラウド同期・アカウント・オンライン対戦
- 課金によるサブスク収益（チップ/寄付のみ）
- Android / Web 版（将来検討。コアは移植しやすい設計にする）
- AIが「任意コード」を生成・実行すること（安全上・規約上、永久に対象外）
- 世界知識を要する高度推論（オンデバイスモデルの守備範囲外。式生成は構造化タスクに分解して対応）

## 4. 用語定義

| 用語 | 定義 |
|---|---|
| **テンプレート（Template）** | あるゲームの採点盤の定義一式（フィールド・レイアウト・式・勝利条件）。AI生成または手動編集で作られ、端末に保存される。 |
| **スキーマ（Schema）** | テンプレートのデータ構造そのもの。本書 §7 で定義する宣言的JSON。 |
| **対局 / ゲームインスタンス（Game）** | テンプレートを用いて実際にプレイした1回分。プレイヤーと記録値を持つ。 |
| **フィールド（Field）** | 採点に使う1つのデータ項目（例: 得点、ラウンド数、ペナルティ）。 |
| **レイアウトノード（LayoutNode）** | 画面の見た目を表す部品ツリーの1要素（スタック・カウンタ・表など）。 |
| **式（Expression）** | サンドボックス化された安全な計算式（合計・順位・勝敗などを算出）。 |
| **レンダラ（Renderer）** | スキーマを解釈してSwiftUIのネイティブ画面を描画する固定エンジン。 |

## 5. 要件定義

### 5.1 ペルソナ
- **P1: 自作・マイナーゲーム愛好家** — 既存アプリに自分のゲームがない。紙でやっている集計を楽にしたい。
- **P2: ボード/カードゲーム会の主催者** — ゲームごとに最適な採点画面を素早く用意したい。
- **P3: ライト層** — 友人との点数つけを、説明するだけで始めたい（細かい設定は触りたくない）。

### 5.2 主要ユースケース
1. **UC-01 新しい採点盤を作る**: 「4人でやるトリックテイキング。各ラウンドで予想と実取りが一致したら10点＋取り数、外したら0点。10ラウンドで合計最大が勝ち」と説明 → AIが画面を生成 → 微調整 → 保存。
2. **UC-02 対局する**: 保存済みテンプレを選び、プレイヤー名を入れて開始。各操作で点を入力し、合計・順位が自動更新。
3. **UC-03 勝敗を確定する**: 終了条件を満たすと勝者をハイライト表示。履歴に保存。
4. **UC-04 履歴を見る/再戦する**: 過去対局を閲覧、同設定で再戦。
5. **UC-05 テンプレを共有する**: テンプレJSONを書き出し、共有シートで友人に送る／受け取って取り込む。
6. **UC-06 AI非対応端末で使う**: プリセット or 取り込んだテンプレで対局（生成はできないが利用は可能）。

### 5.3 機能要件（Functional Requirements）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | 自然言語のゲーム説明を入力できる | Must |

| FR-03 | 生成中はストリーミングで進捗/部分結果を表示する | Should |
| FR-04 | 生成結果をサンプルデータ付きでプレビューできる | Must |
| FR-05 | 生成結果を手動編集できる（フィールド名・配置・式・勝利条件） | Must |
| FR-06 | テンプレを命名して端末に保存できる | Must |
| FR-07 | テンプレ一覧から対局を開始できる（人数・名前・チーム設定） | Must |

## 6. システム方式設計（アーキテクチャ）

### 6.1 全体構成（レイヤ）

```
┌─────────────────────────────────────────────┐
│ Presentation 層 (SwiftUI)                    │
│  - 生成画面 / プレビュー / 編集 / 対局 / 履歴 │
├─────────────────────────────────────────────┤
│ Domain / Engine 層 (Swift Package: ScoreForgeKit) │
│  - SchemaModel       : 宣言的スキーマ型定義   │
│  - Renderer          : スキーマ→SwiftUI描画   │
│  - ExpressionEngine  : 安全な式パーサ/評価器  │
│  - GameRuntime       : 状態管理・再計算・勝敗 │
│  - Generation        : AI生成パイプライン     │
│  - Validation/Repair : スキーマ検証・自動修復 │
├─────────────────────────────────────────────┤
│ Platform 層                                   │
│  - FoundationModels  : オンデバイスLLM        │
│  - SwiftData         : ローカル永続化         │
│  - StoreKit(任意)    : チップ                 │
└─────────────────────────────────────────────┘
```

### 6.2 技術スタック
- **言語/UI**: Swift / SwiftUI（iOS 26 SDK）
- **AI**: FoundationModels フレームワーク（`LanguageModelSession`、`@Generable` によるGuided Generation／構造化出力）
- **永続化**: SwiftData（テンプレ・対局・履歴）
- **式評価**: 自作の軽量サンドボックスDSL（NSExpression等の汎用評価は安全性の観点から不採用）
- **配布/OSS**: GitHub。コアは Swift Package として独立リポジトリ化可能に。
- **収益（任意）**: GitHub Sponsors、StoreKit の消耗型IAP（チップ）。

### 6.3 重要な設計判断（ADR要約）
1. **AI出力は宣言的スキーマに限定** — 任意コード生成は安全・規約・検証性すべてで不利。スキーマ＋固定レンダラなら安全に高い自由度を出せる。
2. **生成は分解（多段）** — 約3Bのオンデバイスモデルは「世界知識・高度推論」が苦手なため、生成を「構造分類→フィールド→式/勝利条件→レイアウト」の小タスクに分割し、各段でGuided Generationを使い信頼性を上げる。
3. **生成は1回・以後は再利用** — レイテンシ/トークン節約。生成物＝資産。
4. **オフライン完結** — サーバーレス＝費用ゼロ＆プライバシー。共有はファイルで代替。
5. **コアの部品化** — 「OSSな部品」という当初目標を満たし、将来の移植（Android/Web）も視野に。

## 7. 詳細設計：採点盤スキーマ（DSL）

本プロダクトの心臓部。AIが生成し、レンダラ／ランタイムが解釈する宣言的データモデル。
Lv3（独自計算式・勝利条件・条件分岐）を表現できる。

### 7.1 スキーマ全体像

```jsonc
{
  "schemaVersion": 1,
  "id": "uuid",
  "name": "コントラクト・ブリッジ風採点",
  "description": "予想と実取りの一致で加点するトリックテイキング",
  "origin": "ai",                 // ai | manual | preset | imported
  "iconSystemName": "suit.spade",
  "themeColorHex": "#2E5BFF",

  "players": {
    "min": 2, "max": 6, "default": 4,
    "teams": false
  },

  "structure": "rounds",          // freeform（累積） | rounds（ラウンド表）
  "rounds": { "fixed": false, "maxRounds": 13 },

  "fields": [ /* §7.2 */ ],
  "actions": [ /* §7.3 */ ],
  "formulas": [ /* §7.4 */ ],
  "layout": { /* §7.5 */ },
  "winCondition": { /* §7.6 */ }
}
```

### 7.2 Field（データ項目）

```jsonc
{
  "id": "bid",
  "label": "予想",
  "type": "integer",          // integer | number | text | bool | select
  "scope": "perPlayerPerRound", // global | perPlayer | perPlayerPerRound | perRound
  "default": 0,
  "min": 0, "max": 13,
  "options": null              // type=select のときの選択肢 [{value,label}]
}
```

- `scope` がデータの粒度を決める。`perPlayerPerRound` ならプレイヤー×ラウンドのセル。
- 値域 `min/max` はランタイムが入力時に強制。

### 7.3 Action（操作ボタン／効果）
ボタン等の操作が、どのフィールドをどう変えるかを宣言。条件分岐（Lv3）を持てる。

```jsonc
{
  "id": "plus5",
  "label": "+5",
  "iconSystemName": "plus.circle",
  "effects": [
    {
      "target": "score",
      "op": "add",            // set | add | subtract | toggle | applyExpression
      "value": 5,
      "when": null            // 省略可。式が真のときのみ適用
    }
  ]
}
```

`applyExpression` を使うと、効果自体を式で表現できる（例: 取り数に応じた加点）。

### 7.4 Formula（派生値・集計）
合計・順位・ボーナスなどの計算を式で宣言。`display:true` なら画面にも表示。

```jsonc
[
  {
    "id": "roundScore",
    "label": "ラウンド得点",
    "scope": "perPlayerPerRound",
    "expression": "field('bid') == field('won') ? 10 + field('won') : 0",
    "display": true
  },
  {
    "id": "total",
    "label": "合計",
    "scope": "perPlayer",
    "expression": "sumRounds('roundScore')",
    "display": true
  },
  {
    "id": "rank",
    "label": "順位",
    "scope": "perPlayer",
    "expression": "rankDesc('total')",
    "display": true
  }
]
```

依存関係は有向非巡回（循環参照は検証で禁止）。再計算はトポロジカル順で実行。

### 7.5 Layout（画面構成）
再帰的な部品ツリー。コンテナ（スタック/グリッド/カード）とリーフ（カウンタ等）からなる。

```jsonc
{
  "type": "vstack", "spacing": 12,
  "children": [
    { "type": "scoreTable",                 // ラウンド×プレイヤーの表
      "rowField": "round", "columnGroup": "player",
      "cellFields": ["bid", "won", "roundScore"] },
    { "type": "hstack", "children": [
      { "type": "counter", "field": "won", "step": 1, "label": "実取り" },
      { "type": "stepper", "field": "bid", "label": "予想" }
    ]},
    { "type": "label", "bind": "total", "style": { "fontScale": 1.4, "emphasis": true } },
    { "type": "actionBar", "actions": ["plus5", "nextRound"] }
  ]
}
```

レンダラがサポートするリーフ部品（v1）:
`counter` / `stepper` / `numberInput` / `textInput` / `toggle` / `segmented(select)` /
`label(bind)` / `badge` / `scoreTable` / `playerHeader` / `actionBar` / `spacer` / `divider`。

各ノードは任意で `style`（サイズ・色・整列・フォント倍率・強調）を持つ。
**未知の type が来た場合**は安全な代替（ラベル＋警告）に縮退（フォールバック）。

### 7.6 WinCondition（勝敗判定）

```jsonc
{
  "type": "highestTotal",     // highestTotal | lowestTotal | firstToReach
                              // | afterNRounds | customExpression
  "scoreFormula": "total",
  "target": null,             // firstToReach のときの目標値
  "rounds": 13,               // afterNRounds のとき
  "tieBreaker": "fewestRounds", // none | fewestRounds | headToHead | customExpression
  "customExpression": null
}
```

ランタイムは毎更新で終了条件を評価し、満たせば勝者集合（同点は複数可）を確定。

### 7.7 具体例（最小フリーフォーム：UNO風）

```jsonc
{
  "schemaVersion": 1, "name": "UNO風（手札ペナルティ累積）",
  "players": { "min": 2, "max": 10, "default": 4, "teams": false },
  "structure": "freeform",
  "fields": [
    { "id": "penalty", "label": "失点", "type": "integer", "scope": "perPlayer", "default": 0, "min": 0 }
  ],
  "actions": [
    { "id": "add", "label": "失点を加える", "effects": [
      { "target": "penalty", "op": "applyExpression", "value": "field('penalty') + input()" }
    ]}
  ],
  "formulas": [
    { "id": "total", "label": "累計失点", "scope": "perPlayer", "expression": "field('penalty')", "display": true },
    { "id": "rank",  "label": "順位",     "scope": "perPlayer", "expression": "rankAsc('total')", "display": true }
  ],
  "layout": { "type": "vstack", "children": [
    { "type": "playerHeader" },
    { "type": "counter", "field": "penalty", "step": 1 },
    { "type": "label", "bind": "total" }
  ]},
  "winCondition": { "type": "firstToReach", "scoreFormula": "total", "target": 500, "tieBreaker": "none" }
}
```

## 8. 詳細設計：安全な式エンジン（ExpressionEngine）

### 8.1 方針
任意コード実行を避けつつLv3の表現力を出すため、**専用の小さな式DSL**を定義し、
ホワイトリスト関数のみを持つツリーウォーク評価器で解釈する。

### 8.2 文法（概略 EBNF）
```
expr     := ternary
ternary  := or ("?" expr ":" expr)?
or       := and ("||" and)*
and      := cmp ("&&" cmp)*
cmp      := add (("=="|"!="|"<"|"<="|">"|">=") add)*
add      := mul (("+"|"-") mul)*
mul      := unary (("*"|"/"|"%") unary)*
unary    := ("!"|"-")? primary
primary  := number | string | bool | call | "(" expr ")"
call     := ident "(" (expr ("," expr)*)? ")"
```

### 8.3 組み込み関数（ホワイトリスト）
| 種別 | 関数 | 意味 |
|---|---|---|
| 参照 | `field('id')` | 現在スコープのフィールド値 |
| 参照 | `input()` | 直近のユーザー入力値（Action内） |
| 参照 | `round(n,'id')` | 指定ラウンドの値 |
| 集計 | `sumRounds('id')` `avgRounds('id')` | 全ラウンド集計 |
| 集計 | `sum('id')` `max('id')` `min('id')` `count('id')` | 全プレイヤー集計 |
| 順位 | `rankDesc('id')` `rankAsc('id')` | 降順/昇順の順位 |
| 数学 | `abs` `round` `floor` `ceil` `min` `max` `clamp(x,lo,hi)` | 基本数学 |
| 論理 | `if(cond,a,b)` | 条件分岐 |

- **禁止**: ループ、再帰呼び出し、I/O、時刻取得、乱数（必要なら別途専用の安全API）、任意プロパティアクセス。
- **上限**: 評価ノード数・呼び出し深さに固定上限。超過時はエラーで停止。
- **決定性**: 同じ入力に対し常に同じ結果。テスト容易。

### 8.4 評価フロー
1. パース（字句→構文木）。失敗時は構文エラーを保持。
2. 依存解決（formula間のDAG構築、循環検出）。
3. トポロジカル順に評価し、各スコープ（global/perPlayer/perRound/セル）の値を確定。
4. 例外（0除算・型不一致・上限超過）は安全に握りつぶし、当該値を「—」表示＋警告。

## 9. 詳細設計：AI生成パイプライン

### 9.1 全体フロー
```
ユーザーの自然言語説明
        │
        ▼
[0] 可用性チェック（SystemLanguageModel.availability）
        │ 利用可
        ▼
[1] 構造分類      → structure / players / 採点方向 を構造化出力
        ▼
[2] フィールド生成 → fields[] を生成（型・scope・値域）
        ▼
[3] ロジック生成   → actions[] / formulas[] / winCondition を生成
        ▼
[4] レイアウト生成 → layout（失敗時はfieldsから自動既定レイアウト）
        ▼
[5] 検証 → 不正なら[6]修復(最大2回) → なお不正ならフォールバック
        ▼
[7] プレビュー（サンプルデータ） → 手動編集 → 保存
```

### 9.2 なぜ多段か
オンデバイスモデルは要約・抽出・分類・構造化出力は得意だが、長く複雑な一括生成は不安定。
タスクを小さく割り、各段で **Guided Generation（`@Generable` 構造体＋制約）** を使うことで、
出力フォーマットを強制し、成功率と検証容易性を高める。

### 9.3 Guided Generation の型イメージ（Swift, 概念コード）
```swift
@Generable
struct GeneratedField {
    @Guide(description: "スコアに使う項目の短い日本語名") var label: String
    @Guide(description: "integer|number|text|bool|select のいずれか") var type: String
    @Guide(description: "global|perPlayer|perPlayerPerRound|perRound") var scope: String
    @Guide(.range(0...999)) var defaultValue: Int
}

@Generable
struct GeneratedStructure {
    @Guide(description: "rounds か freeform") var structure: String
    @Guide(.range(1...12)) var defaultPlayers: Int
    @Guide(description: "高い方が勝ちなら true") var higherIsBetter: Bool
}
```
※ 実際のスキーマ確定値（id採番・式の整合）はアプリ側で補完・正規化する。

### 9.4 プロンプト設計の要点
- **役割固定**: 「あなたはスコア採点盤の設計者。出力は指定スキーマのみ」。
- **少数事例（Few-shot）**: 代表ゲーム3〜5種（累積失点系／ラウンド表系／一致ボーナス系／最少点勝ち系）を同梱し、説明→スキーマの対応を提示。
- **語彙の固定**: 関数名・type名・scope名を列挙し、それ以外を使わせない。
- **分解質問**: 説明が曖昧な場合は、生成前に最大1〜2問だけ選択式で補足（人数？高い方が勝ち？ラウンド制？）。

### 9.5 検証（Validation）と自動修復（Repair）
検証項目（一部）:
- 参照整合: formula/action が存在する field を参照しているか。
- 型整合: 演算対象の型が妥当か。
- 循環参照: formula 依存に閉路がないか。
- 勝利条件: 参照する scoreFormula が存在し評価可能か。
- レイアウト: 未知 type / 不正バインドがないか（あれば安全代替へ）。

不正時は **エラー要約をモデルに戻して再生成（最大2回）**。
なお不正なら、抽出済みの fields から **既定テンプレ（表＋カウンタ＋合計＋順位）** を機械的に構築して提示（必ず動く状態を保証）。

### 9.6 失敗・低品質時のUX
- 「うまく作れなかったら直せる」前提。プレビューは常に手動編集可能。
- 「近いプリセットから始めて説明で微修正」する導線も用意。

## 10. 詳細設計：ランタイム・レンダラ・画面

### 10.1 GameRuntime（状態管理）
- 対局開始時にスキーマからプレイヤー×フィールドの**可変状態ストア**を生成（Observable）。
- 操作 → 効果適用 → 依存formula再計算（DAG順）→ UI反映 → 自動保存。
- Undoスタックを保持（FR-11）。

### 10.2 Renderer（スキーマ→SwiftUI）
- LayoutNodeツリーを再帰的にSwiftUIビューへ写像。
- バインド（`label.bind` 等）はランタイムの算出値に接続しリアクティブ更新。
- スタイルは安全な範囲にクランプ（極端なフォント倍率・色は丸める）。
- WebView/JS不使用。すべてネイティブ部品。

### 10.3 画面一覧と遷移
```
[ホーム/テンプレ一覧]
   ├─(＋)→ [新規作成: 説明入力] →(生成)→ [プレビュー/編集] →(保存)→ 一覧へ
   ├─ テンプレ選択 → [対局セットアップ(人数/名前/チーム)] → [対局画面]
   │                                                   └→(終了)→ [結果/勝者]
   ├─ [履歴] → 対局詳細 → 再戦
   └─ [設定] (テーマ/言語/インポート/エクスポート/チップ/AI可否表示)
```

### 10.4 主要画面の要件
- **説明入力**: 自由記述＋（任意の）補足選択。AI不可端末では非表示にしプリセット導線へ。
- **プレビュー/編集**: サンプルデータで実挙動を確認。フィールド名・配置・式・勝利条件をフォームで編集。
- **対局画面**: スキーマ通りの操作部品。合計/順位を常時表示。中断＝自動保存。
- **結果**: 勝者ハイライト、同点表示、履歴へ保存。

## 12. App Store・ライセンス・配布

### 12.1 App Store規約上の整合
- **2.5.2（外部コード実行禁止）**: AIは宣言的スキーマのみ生成、固定レンダラが解釈。実行コードのDL/評価はしない → 適合。
- **4.3（重複/スパム）**: 単なるスコアアプリではなく「AIビルダー」という差別化で対応。
- **プライバシー**: データ収集なし（Nutrition Label は "Data Not Collected" を想定）。

### 12.2 ライセンス選定（要決定）
| 候補 | 長所 | 短所 | 適性 |
|---|---|---|---|
| **MIT** | 部品として最も再利用されやすい。採用障壁が低い | 改変版がクローズドにされ得る | コアを「部品」として広めたいなら最有力 |
| Apache-2.0 | MIT同様＋特許条項 | ファイルがやや厳格 | 企業利用も視野なら良 |
| GPLv3 | 派生物もOSSを強制 | 取り込み障壁が高い | 思想として「常に自由」を守りたいなら |

> 当初目標「OSSな部品」を重視するなら **コアエンジン=MIT（またはApache-2.0）** を推奨。
> アプリ全体の思想統一を優先するなら GPLv3 も選択肢。**最終決定は要確認。**

### 12.3 収益（任意）
- GitHub Sponsors / Buy Me a Coffee へのリンク。
- アプリ内「チップ」: StoreKit 消耗型IAP（機能制限なしの純粋な投げ銭）。
- 無料OSSと矛盾しない（無料配布＋任意寄付）。

## 13. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| オンデバイスモデルがLv3の式生成を外す | 生成品質低下 | 多段分解＋Guided Generation＋検証/修復＋手動編集＋プリセット起点 |
| 対応端末が限定（iOS26+/Apple Intelligence） | 利用者母数が小さい | 非対応端末でも「プリセット/取り込み/手動作成/対局」は提供。生成は将来BYOK等で拡張余地 |
| 生成レイテンシ | 体感悪化 | ストリーミング表示＋「1回生成→再利用」。プリウォーム活用 |
| 式の暴走/不正入力 | クラッシュ/フリーズ | サンドボックスDSL、評価上限、例外の安全握りつぶし |
| ジャンル飽和 | 埋没 | 「AIで作る」体験を前面に。テンプレ共有でコミュニティ資産化 |
| OSSゆえ無断複製 | 収益機会の喪失 | 元々収益は二の次。ブランド/公式配布/寄付で十分 |
| App Store審査 | リジェクト | 宣言的スキーマ方式・プライバシー設計で規約適合を担保 |

## 15. 受け入れ基準（Acceptance Criteria 抜粋）
- [ ] 代表3ゲームの説明文から、検証を通過するスキーマが生成され、対局まで到達できる。
- [ ] 生成に失敗しても、必ず編集可能な既定テンプレが提示され、操作不能に陥らない。
- [ ] 機内モードで「生成・対局・履歴」すべてが動作する。
- [ ] 不正な式・極端な入力でアプリがクラッシュ/フリーズしない。
- [ ] AI非対応端末で、プリセット/取り込みテンプレでの対局が完結する。
- [ ] ネットワーク通信が一切発生しない（プライバシー要件）。
- [ ] 中断した対局を再開でき、記録が失われない。
